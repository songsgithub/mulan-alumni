# 数字木兰校友会 · 互助团运营系统 — 系统设计

> 依据：《数字木兰校友会互助团SOP-AI豆计划（2026年10月）》的业务链路（活动预算申请 → 项目组审核 → 现场执行 → 活动反馈 → 报销凭证 → 费用管理）与项目组四条要求：
> ① 项目组邀请方可注册，**注册即成为团长**（公众免注册）；团长提活动方案（含经费）→ 项目组审批 → 互助团实施（含反馈）→ 项目组同意报销 → 精选内容推到前端供互联网大众观看。
> ② 项目组上传学习资源，任何人可公开学习。
> ③ 技术栈按图示推荐路线（Next.js + Payload CMS + PostgreSQL），未经同意不擅自调整。
> ④ 站点形态借鉴 Yale Alumni Association / Vital Voices / Obama Leadership Network / Ashoka 的运作机制。

## 一、组织模型：为什么不是"会员制校友会"

数字木兰的共同身份来自**同一批公益项目**（AI 豆计划、民宿管家等），而非同一所学校。因此本系统**只有三种身份**：公众（**无需注册**即可浏览全部公开内容）、**团长账号**、**项目组账号**，外加一个只在 CMS 后台用的 **admin 运营账号**。没有"普通会员"这一档——被项目组邀请注册的人**直接就是团长**，承接"活动经费—反馈—报销"这条需要责任人的链路。

| 层次 | 谁 | 是否有账号 | 核心权责 |
| --- | --- | --- | --- |
| 公众层 | 互联网大众、未经邀请的访问者 | 无 | 浏览精选活动、成长故事、学习资源、合作机会；下载公开学习资料 |
| 核心层 | 核心成员（团长 / 骨干 / 成员） | 有（凭邀请码注册） | 参与团内活动、提交反馈、查看本团内部信息 |
| 治理层 | 项目组（审核 / 财务 / 发布） | 有（后台账号） | 邀请成员、审批活动方案、核定报销、发布学习资源、精选内容推送到前端 |

三个外部借鉴点落到系统里的具体机制：

- **借鉴 Yale：支持多种互助团自主发展。** 互助团（`cohorts`）按地域 / 职业 / 兴趣自主形成，项目组只提供规则、工具包与资金，不代替团长策划。
- **借鉴 Vital Voices：长期支持与资源连接。** 导师 / 企业 / 合作机构以 `partners` + `opportunities` 呈现，不要求普通成员进入复杂社区。
- **借鉴 Obama Leadership Network：跨项目的共同身份。** 首页与"成长故事"按 AI 豆计划 / 民宿管家等不同项目讲同一个"数字木兰校友网络"的故事。
- **借鉴 Ashoka：沉淀经验、共享资源。** 活动的"可复用经验"沉淀为公开学习资源，帮助其他互助团借鉴。

## 二、角色与权限矩阵

| 能力 | 公众 | 核心成员 | 团长 | 项目组 |
| --- | :-: | :-: | :-: | :-: |
| 浏览公开精选内容 / 学习资源 | ✅ | ✅ | ✅ | ✅ |
| 下载公开学习资源 | ✅ | ✅ | ✅ | ✅ |
| 兑换邀请码、注册核心成员 | ✅ | — | — | — |
| 提交活动方案（含经费预算） | ❌ | ❌ | ✅ | ❌（项目组是审批方，不发起） |
| 审批 / 驳回 / 要求修改活动方案 | ❌ | ❌ | ❌ | ✅ |
| 提交活动反馈与凭证 | ❌ | ✅ | ✅ | ❌（实施方是互助团） |
| 提交报销 | ❌ | ❌ | ✅ | ❌（项目组负责核定） |
| 核定报销（可核减） | ❌ | ❌ | ❌ | ✅ |
| 登记基金会到账 | ❌ | ❌ | ❌ | ✅ |
| 上传学习资源 | ❌ | ❌ | ❌ | ✅ |
| 提名精选内容（推荐公开） | ❌ | ❌ | ✅ | ✅（也可直接发布） |
| 精选内容推送到前端 | ❌ | ❌ | ❌ | ✅ |
| 维护互助团与成员名单 | ❌ | ❌ | ✅（本团） | ✅（全部） |
| 新建互助团 / 调整团成员 | ❌ | ❌ | ❌ | ✅ |
| 进入 Payload CMS 后台 | ❌ | ❌ | ❌ | ❌（仅独立 `ops-users` 账号） |

**后台账号（`ops-users`）**：Payload CMS 后台的唯一登录源，等价于全局管理员（可见/可写全部集合），
但**不是业务账号**：进不了工作台，也不承担审批、发起等业务动作。

角色实现方式：Payload `users.role` 为多值数组（`coreMember` / `cohortLead` / `projectTeam`），互助团内的职位由 `cohortMembers.roleInCohort` 承载（`leader` / `core` / `mentor` / `partner`）。访问控制全部走 `src/access/*.ts` 的字段级函数，不依赖界面隐藏。

**执行方 / 审批方分层（2026-10-24 定稿）**

- **执行方 = 互助团**：团长发起活动方案与报销、提交活动反馈、提名精选；核心成员只提交反馈。
- **审批方 = 项目组**：只做三件事——**批准活动、核定报销、登记到账**；不发起活动、不提交反馈、不提交报销。
- **没有写权限的地方照常能看**：菜单只按角色分组，页面不因角色消失；写操作在服务端再兜一次
  （`console/actions.ts` + 集合级 access），前端隐藏只是体面，不是安全。
- **「提名 → 发布」**：团长在活动反馈里推荐 → 项目组在「精选发布」里一键转成公开成果
  （自动带出标题 / 摘要 / 日期 / 人数 / 现场照片 / 所属互助团）。

## 三、SOP 主流程状态机

### 1. 活动方案 `activity-plans`

```
draft ──提交──▶ submitted ──通过──▶ approved ──实施并提交反馈──▶ implemented ──结项──▶ closed
                    │  ▲
        驳回/要求修改 │ └──要求修改── revision_required
                    ▼
                rejected
```

- `draft`：团长编辑中（标题、形式、时间、人数、目标、**预算明细**）。
- `submitted`：进入项目组审批队列，锁定编辑。
- `approved` / `rejected` / `revision_required`：每一次动作写入 `reviews[]`（谁、何时、结论、意见），形成可审计轨迹。
- `implemented`：活动已实施且反馈已提交（由反馈提交自动流转）。
- `closed`：结项，进入报销与后续精选池。

### 2. 活动反馈 `activity-reports`

```
submitted ──采纳──▶ accepted
    │  ▲
    └────要求补充──── revision_required
```

包含：实际日期、实际参与人数、实际支出、内容纪实、照片、满意度与建议（可沉淀为后续学习资源素材）。

### 3. 报销 `reimbursements`

```
draft ──提交──▶ submitted ──同意报销──▶ approved
                      │
                      └──驳回──▶ rejected
```

- 金额三段分离：**预算额（plan.budgetTotal）** → **实际支出（report.actualSpending）** → **申请报销额（reimbursement.total）** → **核定金额（approvedAmount，可核减）**。
- 核减必须填写原因，写入 `reviewNote`。
- 凭证：`items[]` 每行含类别、金额、凭证文件、备注；`voucher` 为付款后回填的凭证。

### 4. 付款记录 `payments`（财务侧在后台登记）

```
pending ──处理──▶ processing ──到账──▶ paid
                     └──失败──▶ failed
```

记录：收款方、金额、方式、计划付款日、实际付款日、流水号、回执文件、备注。`paid` 后回写 `reimbursement.status = paid` 与 `paidAt`。

> 资金链路默认实现为**状态流转 + 凭证归档**（线下打款、线上回填），不直连基金会支付接口；`payments` 集合预留 `externalRef` / `adapter` 字段，便于后续对接。

### 5. 成员邀请 `invitations`

```
pending ──注册成功──▶ accepted
   └──项目组撤销──▶ revoked
```

邀请码唯一、含有效期、绑定邮箱与目标互助团；注册时校验（码存在 / 未过期 / 未撤销 / 邮箱匹配），通过后创建 `users` 账号并自动写入 `cohortMembers`。

## 四、数据模型（Payload Collections）

12 个业务集合 + 2 个上传集合，共 14 个：

> **slug = 网址里那一段，一律是不透明随机串**（14 位小写字母数字，`src/lib/code.ts`）；
> 展示名（name / title）才是中文人话。两者分离，防枚举、防泄漏，名称改了链接也不失效。

| 集合 | slug | 关键字段 | 访问控制 |
| --- | --- | --- | --- |
| 用户 | `users` | email, name, phone, roles[], program, city, bio, avatar, status | 仅本人 + 项目组可读；本人或项目组可写 |
| 邀请 | `invitations` | code, email, roles, cohort, invitedBy, expiresAt, status | 创建/读取：项目组；公开可读仅限"校验码是否有效"（单独 API） |
| 互助团 | `cohorts` | name, slug, region, theme, tags[], leader, status, description, cover, memberCount | 公开可读（`isPublic` 且 active/draft）+ 自己所在的团；写：项目组 |
| 团成员 | `cohort-members` | cohort, user, roleInCohort, joinedAt, active | 内部：同团成员 + 项目组；公开不可读 |
| 活动方案 | `activity-plans` | title, cohort, proposer, form, plannedAt, location, goals, participants, budgetItems[], budgetTotal, budgetPerPerson, budgetCeiling, budgetOverCeiling, budgetStandardNote, status, reviews[] | 内部：项目组 + 本团；创建：团长 / 项目组 |
| 活动反馈 | `activity-reports` | plan, cohort, submittedBy, theme, location, actualAt, actualParticipants, actualSpending, summary, attendees[], feelings[], photos[], spendingProofs[], signupSheet, highlights, survey, overdueDays, status | 内部：项目组 + 本团 |
| 报销 | `reimbursements` | report, plan, cohort, applicant, items[], total, approvedAmount, status, approver, approvedAt, reviewNote, paidAt, paymentRef | 内部：项目组 + 申请人 + 本团团长；创建：团长 / 项目组 |
| 付款 | `payments` | reimbursement, payee, amount, method, status, scheduledAt, paidAt, externalRef, voucher | 仅项目组 |
| 学习资源 | `learning-resources` | title, slug, category, summary, body, file, cover, tags[], visibility, publishedAt, author, downloads | **公开可读**（visibility=public）；写：项目组 |
| 精选发布 | `publications` | title, slug, type, relatedPlan, relatedReport, relatedCohort, excerpt, summary, cover, featured, publishedAt, author | **公开可读**（已到发布时间）；`relatedPlan` / `relatedReport` 经字段级控制仅项目组可见 |
| 合作机会 | `opportunities` | — | **2026-11-05 已下线**：功能未上线、集合零行零引用，连表删了；上线时按 `docs/collections-archive/README.md` 重建 |
| 互助团经验帖 | `toolkits` | — | **2026-11-05 已下线**：同上，配置已归档 |
| **公共媒体** | `media` | filename, alt, visibility | 上传集合。公众仅可见 `visibility=public`；项目组可见全部 |
| **财务凭证** | `finance-evidence` | filename, kind(发票/收据/支付截图/其他), cohort, note | 上传集合。项目组全部可见、核心成员仅本团可见、**公众不可见** |

> `finance-evidence` 独立于 `media` 的原因：报销凭证与付款回单属于内部财务材料，
> 不能因为"公开媒体可匿名下载"而顺带暴露。

## 六、公开与内部的分界（"普通成员不必注册"如何落地）

1. **不建访客账号。** 未登录用户访问 `/`、`/circles`、`/library`、`/about` 全部正常返回 200，
   内容来自 `publications` / `learning-resources` / `cohorts` 的公开查询。
2. **内部数据不进公开查询。** `activity-plans`、`activity-reports`、`reimbursements`、`payments`、
   `cohort-members`、`finance-evidence` 的 read access 均要求登录且角色匹配；
   公开接口（`/api/...`）对这些集合的未授权访问返回 403。
3. **精选内容是"发布"而非"直播"。** 活动结项后由项目组（或团长提名 → 项目组发布）在 `publications` 创建一条发布记录，
   指向该活动，前端只读取 `publications`，因此对外呈现的是"精选 + 已审核"的内容。
4. **公众域不承载规则。** 经费标准、审批流程、凭证要求、角色定义等一律不出现在公众域；
   公众域甚至不提供任何登录入口——登录与邀请注册只存在于管理域。
5. **域名隔离。** 公众域与管理域由 `src/proxy.ts` 按 `Host` 分流，
   管理路径在公众域返回 404，避免"公开站 → 登录入口 → 后台"的路径泄露。

## 八、按 SOP 原文校准的结论（2026 年 10 月定版）

> 本节记录逐条核对《数字木兰校友会互助团SOP-AI豆计划（2026年10月）》原文后的结论，
> 以及结论落到代码的位置。所有阈值均可用环境变量调整，等项目组正式通知后直接改配置即可。
>
> **2026-10-25 第十二轮之三：按 SOP 原文重新核对了一遍活动各环节的要素**，

### 1. 单场活动经费标准与超支处理

**SOP 原文**（4.4 规范有序 / 第三部分 Q5）：

> 单场活动经费人均不超过 30 元**或**单场总预算不超过 500 元（暂定，以最终通知为准），所有支出需符合报销规范。

**结论**：原文是「或」，不是「且」。因此合规判定为

```
预算合计 ≤ 单场上限(500 元)  或  人均 ≤ 人均上限(30 元)
```

等价于本场可报上限 = `max(单场上限, 人均上限 × 预计参与人数)`。

**落到代码**：

| 位置 | 实现 |
| --- | --- |
| `ACTIVITY_BUDGET_CEILING_CENTS` | 单场总预算上限，默认 `50000`（分）= 500 元 |
| `ACTIVITY_BUDGET_PER_PERSON_CEILING_CENTS` | 人均上限，默认 `3000`（分）= 30 元 |
| `src/lib/workflow.ts` | `budgetCeilingCents()` / `perPersonCeilingCents()` / `effectiveBudgetCeilingCents()` / `isOverBudgetStandard()` |
| `activity-plans.budgetCeiling` | 本场实际可报上限（元），只读，系统计算 |
| `activity-plans.budgetPerPerson` | 人均经费（元），只读，系统计算 |
| `activity-plans.budgetOverCeiling` | 是否超标，只读，系统计算 |
| `activity-plans.budgetStandardNote` | 判定说明（含口径与结论），随方案留痕 |

**超支处理**：SOP 写明「暂定，以最终通知为准」，因此不硬性拦截提交，而是
① 提交时在表单实时提示「超出本场经费标准」；
② 方案详情与审批队列高亮标记；
③ **超标方案通过审批时必须填写书面确认意见**（`reviewPlan` 校验），做到超支留痕。

## 第九节 数据库选型评估与活动申请版本追溯（2026-10-31 上线审核）

### 9.1 规模估算

| 项 | 估算 | 落在哪 |
| --- | --- | --- |
| 活动 | 55 团 × 12 场 = 约 660 场 / 年 | 数据库（几 MB） |
| 活动文字（方案、反馈、签到、报销明细、审批与版本） | 每场几十 KB | 数据库（一年 < 100 MB） |
| 活动原图 | 每场 3–10 张、单张 3–8 MB → 约 10–35 GB / 年 | **磁盘卷或对象存储**，不进数据库 |
| 学习视频 | 6 个 × 1 小时，720p–1080p 约 1–2 GB / 个 → 6–12 GB / 年 | 同上 |
| 并发 | 月底 / 活动后 5 天内多个团长同时提交反馈、上传照片 | — |

### 9.2 结论：换成 PostgreSQL（已执行）

数据量本身 SQLite 撑得住（文件都不在库里）。换库的理由是**可靠性与运维**，不是容量：

1. **生产根本跑不了**：原有迁移是 SQLite 方言，`docker compose` 里的 PostgreSQL 一条都执行不了——开发与生产是两套结构。
2. **SQLite 在这个项目里一直在打补丁**：dev push 会删掉反向关系列（每次启动要跑补列脚本）、建索引非幂等、
   删账号撞 NOT NULL 只能直连 SQL、跑种子必须先停服务（`SQLITE_BUSY`）。
3. **并发写**：SQLite 单写者；月底集中提交 + 上传时，写请求会排队甚至超时。
4. **运维**：`pg_dump` 在线备份、时间点恢复、托管数据库（阿里云 RDS 等）、连接池与监控都是现成的。

执行：迁移按 PostgreSQL 重新生成（`src/migrations/*_initial.ts`），`scripts/migrate-sqlite-to-postgres.mjs`
搬完全部数据（逐表核对行数），`payload.config.ts` 只保留 PostgreSQL 适配器且 `push: false`。

**文件存储**：原图与视频放 `media/` 磁盘卷（compose 已挂卷）或 S3 兼容对象存储（配置 `S3_*`）。
上线建议：一年 50 GB 以内放磁盘卷 + 每日 `scripts/backup.sh` 异地同步即可；超过或需要 CDN 再上对象存储。
⚠️ 启用 S3 前需改两处直接读本地磁盘的代码：PDF 内联图片（`lib/pdf-assets.ts`、`lib/activity-pdf-data.ts`）、活动照片打包下载（`api/activity-photos`）。

### 9.3 活动申请版本追溯

**问题**：一份申请会「提交 → 驳回 → 修改 → 再提交」多轮，原来只有审批记录，
看不出上一版写了什么、改了哪里、每条审批意见是针对哪一版。

**设计**（`collections/ActivityPlans.ts` + `lib/plan-versions.ts`）：

| 数据 | 何时写 | 内容 |
| --- | --- | --- |
| `versions[]` | 每次**提交**申请 | 版本号、提交时间、提交人（关系 + 姓名快照）、申请内容快照（主题 / 类别 / 形式 / 时间 / 地点 / 人数 / 预算明细 / 预算合计） |
| `reviews[].version` | 每次**审批** | 这条审批针对的版本号（= 审批那一刻最新的版本） |

- 版本只追加、不修改：集合 REST 写入只给后台账号，服务端动作是唯一写入口；提交后申请内容被集合钩子整体锁定。
- 展示（团长端、项目组端、PDF 同一个组件 `PlanHistory`）：每一版的提交信息 + 它的审批结论 + 与上一版的逐项差异。
- 差异口径：字段逐项比较；预算明细按「费用类别 + 明细项 + 事项说明」配对，分成新增 / 删除 / 金额或备注变化；另列预算合计。
- 旧数据：已通过的申请用当前内容补第 1 版（提交后内容是锁定的）；被驳回过的标「未留档，无法逐项对比」，不编造历史。
